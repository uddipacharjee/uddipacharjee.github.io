Eclipse Dataspace Components (EDC) with Spring Boot

By Uddip Acharjee Shuvo28 October 202611 min read

A data space lets organizations share data without handing it over unconditionally. Each participant keeps its data, publishes offers with usage policies attached, and only shares under a contract both sides agreed to. Industry networks such as Catena-X in the automotive sector are built this way.

Eclipse Dataspace Components (EDC), originally the Eclipse Dataspace Connector, is a widely used open-source framework for building those connectors, hosted by the Eclipse Foundation. It implements the Dataspace Protocol (DSP), the standard that connectors use to talk to each other. This post explains how a connector works and how to publish data offers into one from a Spring Boot service, based on my EdcOnboardingApplication (Spring Boot 3.3, Java 21).

Versions in this post

The examples use EDC 0.14.1 and its Management API v3, as in the EDC Samples of December 2025. EDC 1.0, in release candidates since September 2026, removed v3 in favour of v4. The concepts are unchanged; the last section lists what is different.

Control plane, data plane and the Dataspace Protocol

An EDC connector has two halves:

  • The control plane holds the offers, answers catalog requests, negotiates contracts and manages transfers. Your own applications drive it through the Management API, which must never be exposed to the internet.
  • The data plane moves the actual data once a transfer has been agreed. The control plane tells it what to send where.

Control planes of different organizations only ever talk to each other over DSP. The protocol builds on DCAT for catalogs and ODRL for policies.

Publishing an offer: three resources

A provider makes data available by creating three things through its Management API, in this order.

1. The asset

An asset describes a piece of data and where it really lives. Its properties are public: they appear in the catalog other participants see. The dataAddress tells the data plane how to fetch the data, and is never shared.

The @vocab entry maps unprefixed keys to EDC’s namespace, which keeps the JSON-LD readable. Anything internal, such as a list of partners allowed to see the asset, belongs in privateProperties, not properties, and credentials belong in a vault, never in the data address.

The ODRL context is not optional

Without the ODRL @context inside policy, keys like permission resolve to EDC’s namespace instead of ODRL’s. The request still succeeds, but the connector may not store your rules as rules, leaving an empty policy that permits everything. After creating a policy, read it back with GET /management/v3/policydefinitions/{id} and check that the permission is there. Also remember that a constraint is only enforced if the connector has a policy function registered for its left operand.

The consumer side

The consumer drives its own connector’s Management API, and that connector does the DSP work with the provider:

  1. Catalog. POST /management/v3/catalog/request with the provider’s DSP address (http://localhost:19194/protocol) returns a DCAT catalog. Each dataset carries an offer under odrl:hasPolicy, whose @id is needed next.
  2. Negotiation. POST /management/v3/contractnegotiations with that offer starts a negotiation. Poll GET /management/v3/contractnegotiations/{id} until the state is FINALIZED (or TERMINATED), and read the contractAgreementId.
  3. Transfer. POST /management/v3/transferprocesses with the agreement id. A push transfer (HttpData-PUSH) sends the data to a destination and ends COMPLETED. A pull transfer (HttpData-PULL) stays STARTED, and the consumer fetches an endpoint data reference from /management/v3/edrs/{id}/dataaddress to call the provider’s public data plane.

What changed in EDC 1.0

The concepts above carry over unchanged. The wire format did not:

  • Management API v4. v3 was deprecated in EDC 0.17 and removed in 1.0. v4 keeps the same resources under /management/v4, but every body needs an explicit @type (Asset, PolicyDefinition, ContractDefinition, Criterion, TransferRequest, CatalogRequest) and uses a new JSON-LD context. See the EDC team’s notes on the Management API versions.
  • Dataspace Protocol 2025-1. The current DSP version is 2025-1. Requests name it as dataspace-protocol-http:2025-1, address …/protocol/2025-1 and include a counterPartyId. The original 0.8 protocol used above was dropped in EDC 0.16.
  • Data planes. The old data-plane framework was replaced by Data Plane Signaling, and the transfer samples were removed from the Samples repository in October 2026. The pinned December 2025 version still works for learning the flow.

For the Spring Boot side, the upgrade means a new base URL and new JSON bodies, which is one more reason to keep every Management API call in a single class.

Checklist

  • Asset, then policy, then contract definition, in that order.
  • Public data in properties; internal data in privateProperties; secrets in a vault.
  • The ODRL context inside every policy, and a read-back to confirm the rules.
  • Asset selectors on the expanded …/ns/id key.
  • All Management API calls in one client class, behind a token, on a private network.
  • Version numbers written down: v3 and DSP 0.8 here, v4 and DSP 2025-1 on EDC 1.0.
