Process a Million-Row File with Spring Batch

By Uddip Acharjee Shuvo28 October 202610 min read

Loading a flat file into a database looks like a ten-line job until the file has a million rows. Read it into a List first and the JVM runs out of heap. Wrap the whole load in one transaction and a bad row near the end throws away everything before it. Spring Batch’s chunk-oriented steps solve both problems: memory stays flat no matter how big the file is, and a failed run picks up where it stopped.

This guide builds a job that imports a fixed-width or CSV file into PostgreSQL, using Spring Boot 3 and Spring Batch 5. It is based on my spring-batch-demo repository, which includes a 51 MB test file of one million fixed-width lines.

How a chunk-oriented step works

A step reads items one at a time until it has a full chunk, runs each item through an optional processor, then hands the whole chunk to the writer. Reading, processing and writing one chunk happen inside a single transaction. If the writer succeeds, the transaction commits and the step starts on the next chunk. If it fails, only that chunk rolls back.

Two consequences matter for large files. Memory use is bounded by the chunk size, not the file size. And because Spring Batch records progress after every commit, a job that dies at row 600,000 can restart at row 600,001 instead of at row 1.

A few details that are easy to get wrong:

  • Order matters in the builder. strict(false) has to come before names(…). names returns you to the outer builder, whose own strict method controls something else: whether a missing input file is an error.
  • Strict lines. By default the tokenizer rejects any line shorter than the last range. Files with trimmed trailing spaces need strict(false) on the fixed-length builder.
  • @StepScope and a job parameter for the path. The reader is created when the step starts, so each run can point at a different file, and the file path becomes part of the job’s identity. That is what makes restarts work, as shown below.
  • targetType maps fields onto a JavaBean by property name. A Java record works too: Spring Batch detects records and calls the canonical constructor.

Writing: batched JDBC beats saving entities one by one

Choosing a chunk size

The chunk size is the commit interval. Small chunks spend their time on commits. Large chunks hold more items in memory, keep transactions open longer, and lose more work when one fails. Somewhere between 100 and 1,000 is a good starting range for simple rows. Then measure instead of guessing. A step listener can log what each run did:

Run the same file with chunk sizes of 100, 500 and 1,000 and compare. The same numbers are stored in the BATCH_STEP_EXECUTION table, so you can also compare runs with a query.

Three things that quietly slow a batch job down

  • spring.jpa.show-sql=true prints every statement: a million INSERTs means a million log lines.
  • Logging every item at INFO in the processor has the same cost. Log per chunk or per step from a listener instead.
  • A database lookup per item, such as checking for duplicates with findByUid, is a million round trips. Load reference data once into a map, or let the database enforce uniqueness as the writer above does.

Multi-threaded steps need a thread-safe reader

Adding .taskExecutor(executor) to a step processes several chunks in parallel, and it is tempting for a CSV import. The catch is that FlatFileItemReader is not thread-safe. Restarting a failed import

Spring Batch identifies a job instance by the job name plus its identifying parameters. When a run fails, launching the same job again with the same parameters is a restart, not a new run. The reader reads the read.count it saved at the last commit and skips straight to that line.

This is why adding a timestamp parameter to every launch is worth a second thought. It makes each run a new instance, which is right for a job that should always start fresh, but it also means a crashed import starts again from line 1. Using the file path as the parameter, as above, gives you a restart for free when the same file is submitted again.

On Spring Boot 4 and Spring Batch 6

Everything above targets Spring Boot 3 and Spring Batch 5. Spring Batch 6, which ships with Spring Boot 4, keeps the same concepts but renames several of the APIs used here:

  • chunk(500, transactionManager) is deprecated. Write .chunk(500).transactionManager(transactionManager).
  • JobLauncher and TaskExecutorJobLauncher are deprecated in favour of JobOperator (TaskExecutorJobOperator), which can also start jobs on a task executor. JobExplorer is deprecated because JobRepository now covers it.
  • Boot 4’s spring-boot-starter-batch keeps job metadata in memory. Restarts need it in the database, so use spring-boot-starter-batch-jdbc.
  • Readers and writers moved to org.springframework.batch.infrastructure.*.
  • In a multi-threaded step, only the processor now runs concurrently; reading and writing happen on one thread.
  • Failed Batch 5 job instances cannot be restarted after the upgrade, so finish or abandon them first.

Checklist

  • Chunk-oriented step, with the chunk size measured rather than guessed.
  • @StepScope reader, with the file path as a job parameter.
  • JdbcBatchItemWriter (or Hibernate batching with sequence ids), plus reWriteBatchedInserts=true on PostgreSQL.
  • No per-item SQL logging, per-item INFO logs or per-item lookups.
  • spring.batch.job.enabled=false and an async launcher with a small pool for jobs started over HTTP.
  • Multi-threaded steps only with a synchronized reader, or partitioning when restarts matter.
