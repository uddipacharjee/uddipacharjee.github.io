Fix JPA N+1 Queries and Open-in-View in Spring Boot

By Uddip Acharjee Shuvo28 October 20269 min read

Two JPA defaults cause most of the database trouble in Spring Boot apps. Lazy associations turn one innocent-looking loop into hundreds of queries: the N+1 problem. And open-in-view, which Spring Boot switches on by default, hides those queries by letting them run anywhere in a request, even while Jackson is writing the JSON response. With ten rows on a laptop neither shows up. With real data, both do.

This guide shows how to see N+1 queries, the four ways to fix them, and why spring.jpa.open-in-view=false belongs in every new project. The examples use Spring Boot 3 and Hibernate 6.

3. Batch fetching as a safety net

Some lazy access is legitimate and hard to predict. Batch fetching makes Hibernate initialize up to N collections at once with an IN (…) query, which turns 1 + 100 queries into 1 + 2:

It does not remove the extra queries, but it caps them. That makes it a good default for the whole application, alongside explicit fetches on the queries you know about.

4. Don’t load entities you are only going to read

A list screen that shows an order number and a count does not need managed entities at all. A constructor expression returns exactly the columns it needs, in one query, with nothing for Hibernate to track:

Spring Data’s interface and class-based projections do the same for derived queries. Use entities when you are going to change them, and projections when you are only going to show them.

Join fetch and pagination don’t mix

join fetch on a collection combined with a Pageable cannot be paged in SQL, because the database sees one row per line, not per order. Hibernate fetches everything and pages in memory, with only a warning in the log. Make that an error:

Then page in two steps: query a page of order ids, and load those orders with an entity graph using findByIdIn(ids).

One more limit: Hibernate refuses to join fetch two List collections of the same entity in one query (MultipleBagFetchException), because the result would be a cartesian product. Fetch the second collection in a separate query, or rely on batch fetching for it.

What open-in-view actually does

On startup, a default Spring Boot app with JPA logs this warning:

With open-in-view on, Spring registers an interceptor that opens a persistence context when a web request starts and closes it only when the response is finished. Lazy associations therefore keep working after your @Transactional service method has returned, including while Jackson serializes an entity in the controller.

That convenience has two costs:

  • Hidden queries. Every lazy association that Jackson touches while writing the response is another SELECT, often an N+1, running outside any transaction and invisible in the service code.
  • Connections held longer. Once the request has used the database, its connection stays checked out until the response is written. Under load, slow clients and large responses hold connections that other requests are waiting for, and the pool runs dry long before the database is busy.

Turn it off

Now the persistence context lives exactly as long as the transaction. Code that relied on open-in-view fails with a LazyInitializationException, and that failure is useful: it points at exactly the data the service forgot to fetch. Fix each one with a join fetch, an entity graph or a projection in the service, and return DTOs rather than entities from your controllers, so serialization never touches the persistence context at all.

On an existing application, switch it off in a branch and run the tests. Every exception that appears is a query that was previously running unnoticed during serialization.

Checklist

  • @ManyToOne and @OneToOne marked LAZY explicitly.
  • Statement-count assertions on the queries that matter.
  • Join fetch or @EntityGraph where you know what you need; projections for read-only lists.
  • hibernate.default_batch_fetch_size as a safety net.
  • fail_on_pagination_over_collection_fetch=true, and two-step paging for collections.
  • spring.jpa.open-in-view=false, with DTOs returned from controllers.
