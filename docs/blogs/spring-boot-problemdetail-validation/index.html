Spring Boot REST Errors with ProblemDetail and Validation

By Uddip Acharjee Shuvo28 October 20268 min read

Ask three Spring Boot APIs for something invalid and you often get three error formats: a Whitelabel page, a JSON blob with a stack trace, and a hand-rolled { "error": "..." }. Every client then needs its own parsing code, and nobody can tell which field was wrong.

RFC 9457 (Problem Details for HTTP APIs, which replaced RFC 7807) defines one JSON shape for errors, and Spring Framework 6 supports it out of the box with the ProblemDetail class. This guide wires Bean Validation and your own exceptions into that format, tests it, and documents it in OpenAPI. It targets Spring Boot 3.

What a problem detail looks like

The response uses the content type application/problem+json and five standard members:

  • type: a URI that identifies the kind of problem. Ideally it points to documentation; the default, about:blank, means “nothing more specific than the status code”.
  • title: a short, human-readable summary of that type.
  • status: the HTTP status code, repeated in the body.
  • detail: an explanation of this particular occurrence.
  • instance: a URI for this occurrence, usually the request path.

Anything else is an extension member. Clients that don’t know an extension ignore it, so adding an errors list for field-level messages is safe.

Checklist

  • Constraints on request records, with @Valid on nested ones.
  • One @RestControllerAdvice extending ResponseEntityExceptionHandler.
  • An errors extension with field paths for validation failures, in both body and parameter validation.
  • Stable type URIs and titles for your own exceptions.
  • A catch-all that logs and returns a generic 500, never a stack trace.
  • MockMvc tests and OpenAPI annotations for the error responses.
