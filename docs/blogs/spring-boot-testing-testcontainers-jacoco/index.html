Testing Spring Boot: Slices, Testcontainers and JaCoCo

By Uddip Acharjee Shuvo28 October 20269 min read

A test suite that takes ten minutes gets skipped. One that mocks everything passes while production breaks. The useful middle is a mix: many fast unit and slice tests, a real database wherever SQL matters, a handful of full-application tests, and a coverage gate so none of it quietly erodes.

This guide builds that mix for a Spring Boot 3 service with Gradle, JUnit 5, Testcontainers and JaCoCo. The coverage setup comes from my EdcOnboardingApplication repository.

Pick the smallest test that proves the point

Spring Boot’s test slices start only part of the application, which makes them much faster than a full @SpringBootTest. Choosing the right one is most of the work:

Unit tests: no Spring at all

Business rules in a service need no application context. With constructor injection, Mockito can build the service directly:

These run in milliseconds, so this is where most of your test cases should live.

Web slice: @WebMvcTest

@WebMvcTest loads controllers, controller advice, Jackson and the MVC infrastructure, but no services or repositories. That makes it the right place to test request mapping, validation, JSON shape and error responses:

@MockitoBean replaces Boot’s @MockBean, which is deprecated since Spring Boot 3.4. For a full example of testing error responses, see Spring Boot REST Errors with ProblemDetail and Validation.

A real PostgreSQL with Testcontainers

Testing repositories against H2 tests H2. PostgreSQL-specific SQL such as ON CONFLICT, jsonb columns or array types either fails or behaves differently, and Flyway migrations written for PostgreSQL may not run at all. Testcontainers starts the real database in Docker for the duration of the tests:

Spring Boot manages the versions. Since Boot 3.1, @ServiceConnection reads the container’s host, port and credentials and configures the DataSource from them, so there is no @DynamicPropertySource boilerplate:

@DataJpaTest runs your Flyway or Liquibase migrations, wraps each test in a transaction and rolls it back afterwards. Replace.NONE stops it from swapping the container for an embedded database.

Keep the context cache warm

Spring caches application contexts between test classes, but only when their configuration is identical. Every different combination of @MockitoBean fields, profiles or properties starts a new context, and each one can take seconds. Keep integration tests on a shared base class or meta-annotation so they reuse one context.

A coverage gate with JaCoCo

JaCoCo measures which lines and branches the tests executed. The Gradle plugin produces a report after every test run:

The HTML report lands in build/reports/jacoco/test/html/index.html. A report on its own changes nothing, though. A verification rule makes the build fail when coverage drops:

Now ./gradlew check, and therefore CI, fails below 80% line coverage. Pick the threshold from where the project is today and raise it over time. Exclude generated code and plain configuration classes, so the number reflects code that has behaviour.

Treat the gate as a ratchet, not a goal. It stops coverage from sliding; it says nothing about whether the assertions are any good. A service tested only for its happy path can still score 90%.

On Spring Boot 4 and Testcontainers 2

Spring Boot 4 moves to Testcontainers 2, which prefixes every module with testcontainers- (for example org.testcontainers:testcontainers-postgresql) and moves container classes into per-module packages, such as org.testcontainers.postgresql.PostgreSQLContainer. The approach above, with slices, @ServiceConnection and a shared container configuration, stays the same.

Checklist

  • Plain JUnit and Mockito for business rules: most of your tests.
  • @WebMvcTest for mapping, validation and error responses.
  • @DataJpaTest against a real PostgreSQL with Testcontainers and @ServiceConnection.
  • A few @SpringBootTest end-to-end paths, sharing one context.
  • One container configuration, reused by tests and local development.
  • A JaCoCo report plus a verification rule wired into check.
