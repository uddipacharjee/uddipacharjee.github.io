Spring Modulith: Build a Modular Monolith in Spring Boot

By Uddip Acharjee Shuvo28 October 20269 min read

Most Spring Boot monoliths start tidy. A year later the order code reads the product tables directly, the product code imports an order DTO, and nobody can change one area without breaking another. Splitting into microservices fixes the coupling, but you pay for it with network calls, separate deployments and data that is only eventually consistent.

A modular monolith is the middle path: one deployable application, with boundaries inside it that are enforced rather than hoped for. Spring Modulith gives a Spring Boot app those boundaries, a test that fails when one is crossed, and documentation generated from the code. The examples come from my modulith repository, a small shop with catalog, orders and inventory modules on Spring Boot 3.4 and Spring Modulith 1.3. Spring Modulith 2.x, for Spring Boot 4, keeps every API shown here.

Modules are packages

Spring Modulith needs no new build structure. Every direct sub-package of your application’s main package is a module:

Types in a module’s top-level package are its API. Everything in a sub-package is internal, even when it is declared public. That last part is the point: Java’s public means “visible to everyone”, and there is no keyword for “visible to my module only”. Spring Modulith adds that rule and checks it.

Add Spring Modulith to the build

Verify the boundaries in a test

One test turns the package conventions into rules the build enforces:

verify() fails the test with a list of violations if:

  • two modules depend on each other in a cycle,
  • a module uses a type from another module’s internal packages, such as orders injecting catalog’s ProductRepository, or
  • a module depends on one it has not declared as allowed (see below).

Because it is a plain unit test, it runs on every build. A boundary violation shows up in a pull request instead of in an architecture review six months later.

Declare which modules a module may depend on

By default a module may use any other module’s API. To make the dependency graph explicit, list the allowed ones on the module’s base package. Anything not listed fails verify():

To allow only a named interface, use the module :: interface form, for example "orders :: order-events". A small shared kernel, such as a PagedResult type every module returns, can be declared an open module, which exposes all of its packages:

Keep open modules small

An open module switches the boundary checks off for its contents. That is fine for a handful of shared value types. It is how a “common” package grows into the tangle you were trying to avoid.

Talk through events instead of calls

Orders validates against catalog with a direct call, because it needs the answer before it can continue. Inventory is different: orders does not need to wait for it, and should not even know it exists. So orders publishes an event after saving:

The dependency now points from inventory to orders, not the other way round. Adding shipping or notifications later means adding a listener, not editing OrderService.

A plain @EventListener runs synchronously, inside the publisher’s transaction. If the inventory update throws, the order rolls back with it. Spring Modulith’s @ApplicationModuleListener and its event publication registry fix that. They are covered in Transactional Outbox with Spring Modulith Events.

Test one module at a time

@ApplicationModuleTest starts only the module the test class lives in, rather than the whole application. Beans from other modules are not created, so dependencies on them are mocked. The Scenario parameter lets a test trigger something and wait for the event it should publish:

@MockitoBean is the Spring Framework 6.2 replacement for Boot’s deprecated @MockBean. The stimulus runs in its own transaction, which commits, so clean up what it created (Scenario has an andCleanup(…) hook for this). The orders module still needs its database, so run this against a real PostgreSQL. The testing guide shows how with Testcontainers.

Modular monolith or microservices?

Modular monolithMicroservices
DeployablesOneOne per service
Calls between partsIn-process method calls and eventsNetwork calls and messaging
ConsistencyLocal transactionsEventual, with sagas or outboxes
Boundaries enforced byTests like verify()Separate codebases and the network
ScalingThe whole applicationEach service on its own
Operational costLowHigh

For most teams, a modular monolith is the better place to start. If a module later needs to scale or deploy on its own, clean boundaries and event-based communication make extracting it a refactoring, not a rewrite.

Checklist

  • One top-level package per business capability.
  • Interfaces and records in the module’s base package; everything else below it.
  • ApplicationModules.of(App.class).verify() in the test suite.
  • allowedDependencies to make the dependency graph explicit, and named interfaces for shared events.
  • Events for anything the caller does not need to wait for.
  • @ApplicationModuleTest for module-level integration tests.
  • Generated documentation, regenerated on every build.
