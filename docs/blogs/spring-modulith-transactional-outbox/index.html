Transactional Outbox with Spring Modulith Events

By Uddip Acharjee Shuvo28 October 20269 min read

When an order is placed, other parts of the system need to react: reserve stock, send a confirmation, publish a message to Kafka. Doing that reliably is harder than it looks. React inside the order’s transaction, and a failure in the stock code cancels the order. React after the commit, and a crash at the wrong moment loses the reaction for good.

The transactional outbox pattern solves this. The event is stored in the same database transaction as the order, then delivered afterwards and retried until it succeeds. Spring Modulith’s event publication registry implements that pattern for ordinary Spring application events. This post continues the shop example from Spring Modulith: Build a Modular Monolith in Spring Boot, on Spring Boot 3.4 and Spring Modulith 1.3.

Why a plain event listener is not enough

The orders module publishes an OrderCreatedEvent after saving, and inventory listens for it:

@EventListener runs synchronously on the publishing thread, inside the order’s transaction. If reserve throws, the order rolls back. If it is slow, placing an order is slow. The modules are separate in the code but still tied together at runtime.

@TransactionalEventListener moves the listener to after the commit. That fixes the coupling, but the event now exists only in memory. If the listener fails, or the application stops between the commit and the listener running, the stock is never reserved and nothing records that it should have been. This is the classic dual write problem: two things that must both happen, and no transaction covering both.

How the event publication registry works

With the registry on the classpath, publishing an event inside a transaction also writes one row per transactional listener into an event_publication table. Because that write happens in the business transaction, the order and its pending events commit together, or not at all.

After the commit, each listener runs. When it returns normally, its publication is marked complete. When it throws, the publication stays incomplete, and the event is still in the database, serialized as JSON, ready to be delivered again.

Setting it up

Pick one registry starter. The JDBC variant works in JPA applications too and can create its own table:

spring-modulith-starter-jpa is the alternative. It stores publications through a JPA entity, so create the table with your migrations (Flyway or Liquibase) like any other.

The jdbc.* settings only apply to the JDBC starter

With the JPA starter on the classpath, every spring.modulith.events.jdbc.* property is silently ignored: no schema, no automatic table. It is an easy mix-up, since both starters write to the same event_publication table. Choose one starter and configure that one.

Listening with @ApplicationModuleListener

@ApplicationModuleListener is shorthand for three annotations:

  • @TransactionalEventListener: runs after the order’s transaction commits, never for a rolled-back order.
  • @Async: runs on another thread, so placing the order does not wait for inventory.
  • @Transactional(propagation = REQUIRES_NEW): the listener gets a transaction of its own.

It relies on Spring’s @Async support, so add @EnableAsync to a configuration class if nothing in your application enables it yet. The registry covers any @TransactionalEventListener, but this one annotation captures the combination you almost always want between modules.

Delivery is at least once

A retried publication runs the listener again. Make listeners idempotent: check whether the reservation for this order number already exists, or rely on a unique constraint, so running twice has the same effect as running once.

Retrying incomplete publications

Incomplete publications stay in the table until something resubmits them. There are two ways to do that.

On restart

This is simple and fits a single instance. With several instances, each one republishes everything on startup, which the Spring Modulith documentation advises against.

On a schedule

On Spring Modulith 2

Spring Modulith 2.x, for Spring Boot 4, extends the registry. Each publication now has an explicit status (published, processing, completed, failed, resubmitted). A staleness monitor flags publications stuck in processing, and FailedEventPublications resubmits failures with options. From 2.1, JDBC schema initialization is on by default. The concepts and annotations in this post stay the same.

Checklist

  • One registry starter (-jdbc or -jpa), and the table created by Modulith or by your migrations.
  • @ApplicationModuleListener between modules, with async execution enabled.
  • Idempotent listeners: delivery is at least once.
  • A retry strategy: republish on restart for one instance, or a scheduled IncompleteEventPublications job.
  • A completion mode or a purge job, so the table doesn’t grow forever.
  • @Externalized for events other services need, so the broker gets the same guarantees.
